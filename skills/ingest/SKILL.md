# ingest：Canon への取り込み

## 原則（必ず守る）
- **根拠（出典）のない値は書かない。推測で埋めない。**
- 値の出典は `.canon/sources/` のアンカー（`<!-- src: ... -->`）と**同じ表記**で書く。アンカーに無い参照は validate で拒否される
- 情報源どうしが一致 → `confirmed`。食い違い → `conflict`（すべての主張を claims に残し、どちらも選ばない）。どこにも無い → `unknown`
- 文書・コード・人の回答は**同格の情報源**。どれが正しいかを AI が決めない
  - 文書に記載なし＋コードに値あり → コードを根拠に `confirmed`（`kind: code`、`パス:行`）。質問にしない
  - 文書とコードが食い違う → `conflict`（コードの主張は `kind: code` の claim）。設計書が古いのか実装が間違っているのかは人が決める
  - どちらにも無い → `unknown`
- スキーマ（`${CLAUDE_PLUGIN_ROOT}/schema/types/`）の必須項目は、値が無くても `unknown` として必ず置く。どの項目が必須かはプロファイル（`.canon/config.yaml` の `profile`、定義は `${CLAUDE_PLUGIN_ROOT}/schema/profiles/`）で変わる
- 必須でない項目は、根拠があるときだけ書く。根拠が無い任意項目を unknown で埋めて質問を増やさない
- 項目がその要素に当てはまらない場合（例：純粋な関数の「状態の変化」）は `status: not_applicable`。ただし根拠が要る：文書にそう書かれていれば document、無ければ AI が決めずに質問にする（選択肢に「該当なし」を入れる）

## 解釈を固定する規則（同じ入力から毎回同じ Canon にするため）
- **振る舞いの単位**：コードの公開関数・処理の入口（API、画面の操作、バッチ）1つにつき1つ。内部の関数は親の振る舞いの処理に含める。コードが無ければ文書の機能の単位
- **試験の単位**：試験関数（`#[test]`、`func TestXxx`、`test_xxx` 等）1つにつき1つ。文書の試験項目が試験関数と対応しなければ別の要素にする
- **要求の単位**：文書の要求1文につき1つ。コードからは要求を作らない（コードは「どうなっているか」で、要求は「なぜ・何を」）
- **必須項目に該当する記述が無いとき**：文書にその項目の記述（受入条件なら受入条件・合格基準として書かれた文）が無ければ、他の記述を読み替えて埋めない。`unknown` にし、候補になる記述（テストの期待結果、関連する文）は質問の options と context に載せる
- **裏付けは全部書く**：同じ値を述べている情報源が複数あれば、1つを `source` に、残りを `also` に書く（文書とコードの両方にあるなら両方）。片方だけにしか書かないと、後の照合ができない
- **情報源の箇所はすべて使う**：取り込み後の `canon gaps` で「出典として使われていない情報源の箇所」が出たら、その箇所の内容を Canon のどこに入れるかを決めて取り込む。入れる場所が無い（スキーマに型・項目が無い）なら、取り込まずにその旨を報告する（スキーマ改修候補）

## 型と、要素を作る単位
設計書6種（要件定義・基本設計・詳細設計・単体／結合／総合試験）の欄は、すべてどれかの型の項目に対応している。情報源にあるものは、型を問わず取り込む。

| 型 | 作る単位 | 主な情報源 |
|---|---|---|
| prj（プロジェクト） | **必ず1件（PRJ-001）**。目的・概要・対象外・前提・関係者・業務の流れ・試験環境など、プロジェクト全体の情報 | 文書の冒頭・はじめに・体制・試験計画。無ければ必須項目を unknown にして質問する |
| req（要求） | 文書の要求1文につき1つ。非機能要求は nfr_category（IPA 非機能要求グレードの大項目）も書く | 要件定義書、README の目的・約束（「Bounded」「never panics」なども要求） |
| scr（画面） | 文書の画面1つ。文書が無ければ、コードの画面の入口（ウィンドウ、ルート、ダイアログ）1つ | 画面設計、UI のコード |
| rpt（帳票） | 文書の帳票・出力ファイル1つ | 帳票設計 |
| ifc（外部IF） | 外部とのやり取り1種類（相手×方式）につき1つ。ほかのアプリの起動、ファイル形式の読み書き、外部 API、OS の機能 | IF 設計、連携の記述、それを行うコード |
| dat（データ） | 保存・受け渡しするデータの単位（テーブル、ファイル形式、その中の構造）1つ。処理の中の一時的な変数は作らない | データ設計、ファイル形式の記述、型定義 |
| bhv（振る舞い） | 下の規則（公開関数・処理の入口1つにつき1つ） | 詳細設計、コード |
| cmp（構成要素） | 文書の構成要素1つ。コードはパッケージ・クレート・モジュール（ディレクトリの単位）1つ | 方式設計、ディレクトリ構成、Cargo.toml・go.mod など |
| adr（設計判断） | 文書が「何を決めたか」と「なぜか」のどちらかを書いている判断1つ（「〜のため」「〜ではなく〜にした」）。片方しか無ければもう片方を unknown にして質問する | 設計書の方針・理由の文、ADR |
| term（用語） | 文書の用語集の1語。用語集が無ければ、文書が意味を述べている言葉（「X とは」「X: …」「X（…のこと）」）だけ。AI が定義を作らない | 用語集、本文の定義 |
| tst（試験） | 下の規則（試験関数1つにつき1つ） | 試験仕様書、テストコード |

- 要素どうしのつながりもリンクで書く（出典付き）：振る舞い→データ・外部IF は `uses`、振る舞い→構成要素は `realized_by`、画面・帳票・振る舞い→要求は `derived_from`、試験→振る舞い・要求は `verifies`、要素→設計判断は `decided_by`
- 試験の観点区分（viewpoint）は、試験の期待結果で決める：エラー・拒否・壊れた入力を確かめる → `abnormal`、上限・下限・境目の値を確かめる → `boundary`、それ以外 → `normal`。出典は試験の期待結果（文書）かテストコードの位置。期待結果がどちらとも読めるなら unknown にして質問する
- 試験種別（test_type）は総合・受入試験だけ必須。結合試験は受け渡すデータ（interface_data）が必須

## 手順
1. `canon gaps` で現状を見る。`.canon/sources/` を読み、対象範囲の要素候補を上の表の型ごとに洗い出す
2. 要素ごとに `canon next-id <型>` で ID を取る（既存の要素と同じものなら新しく作らず更新する）
3. スキーマの項目ごとに、全情報源とコードから根拠を探し、上の原則で状態を決める
4. **先に質問を作る**：`canon next-id question` で ID を取り、`.canon/questions/Q-xxx.yaml` を書く（書式は ask スキル）。**1問1判断**：1つの質問は1つの要素の1つの決めごとを聞く。まとめてよいのは、1つの答えで本当に全部が決まるときだけ（asks_for は3項目まで。超えると validate が警告する）
5. 要素を `.canon/canon/<型>/<ID>.yaml` に書く。リンク（derived_from・verified_by・verifies 等）にも出典を付ける（トレーサビリティ表など）
6. `canon validate` を実行し、エラーが 0 になるまで直す（書き込み時にもフックが検査する）
7. `canon gaps` で「出典として使われていない情報源の箇所」を確認し、上の規則に従って取り込むか報告する
8. `canon crosscheck` を実行する。設計書の識別子のうち、同じ要素が出典にしているコードに見当たらないものが `.canon/crosscheck.yaml` に一覧になる。**AI は一致・不一致を判断しない**（resolution は open のまま。人が決める）
9. 利用者に報告する：取り込んだ要素数、確定率、必須の空白・矛盾と質問、情報源の網羅、crosscheck の確認待ちの件数

## 量が多いとき（分けて進める）
1つのエージェントが読み切れない量（目安：コード数万行、文書数十件を超える）なら、分けて並行で進める。

1. **分け方を決めて報告する**（主のエージェント）：まずアプリ・サービス・パッケージなどディレクトリの単位で分け、大きすぎればその下のモジュールで分ける。各分割に「名前・コードの範囲・情報源のファイル」を決める。全体を説明する文書（README、アーキテクチャ、試験計画）は「全体」の分割にする
2. **分割ごとにサブエージェントを起動する**（Agent ツール、並行でよい）。渡すもの：担当する範囲、この ingest スキルの規則、次の約束
   - 担当範囲の要素だけを作る。範囲の外の要素は作らない・書き換えない
   - **共有されるもの**（プロジェクト全体の情報 PRJ、複数の分割で使う用語・データ形式・分割どうしの外部IF）は作らず、候補として報告する（名前、出典、どの分割で使うか）
   - 担当外の要素へのリンクは書かず、「どの要素から、何を指す予定か、出典」を報告する
   - ID は必ず `canon next-id` で取る（取った時点で予約されるので、並行でもぶつからない）。番号を自分で付けない
   - 終わったら `canon validate` を実行し、自分の範囲のエラーを 0 にする
3. **全体の工程**（すべての分割が終わってから主のエージェントが行う）
   - 報告された共有の候補から、PRJ-001・用語・データ形式・外部IF を1つずつ作る（同じものは1つにまとめ、出典は also にすべて書く）
   - 報告された分割をまたぐリンクを書く（相手の要素を探し、出典付きで）
   - 構成要素の親子を `part_of` でつなぐ（クレート → アプリなど）
   - `canon validate` と `canon gaps`（出典として使われていない情報源の箇所）を確認する
4. **途中で止まったら**：`canon gaps` の未使用の箇所と既存の要素から、終わっていない分割を見つけてそこから再開する。終わった分割はやり直さない

## 要素の書式
```yaml
id: BHV-001
type: bhv
name: 注文履歴の検索処理
fields:
  summary:
    value: "条件に合う会員本人の注文を新しい順に返す"
    status: confirmed
    source: { kind: document, ref: "詳細設計書 v2.0 シート7 B3:F5" }
    also:
      - { kind: code, ref: "src/order/search.go:40-60" }
  timeout:
    status: unknown
    question: Q-003
  error_cases:
    status: conflict
    claims:
      - value: ["該当なしの場合は空の一覧を返す"]
        source: { kind: document, ref: "詳細設計書 v2.0 シート7 B30" }
      - value: ["該当なしの場合はエラー E-404 を返す"]
        source: { kind: code, ref: "src/order/search.go:56" }
    question: Q-002
links:
  - type: derived_from
    target: REQ-001
    source: { kind: document, ref: "基本設計書 v1.2 トレーサビリティ表" }
```
- 単位がある項目（timeout など）は `unit` を付ける（使える単位はスキーマ参照）
- コードの位置は対象プロジェクトのルートからの相対パス `パス:行` または `パス:開始-終了`
